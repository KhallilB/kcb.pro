# Progress ledger and generated book

Date: 2026-10-22
Status: approved in conversation; spec review passed; awaiting owner review

## Goal

Show how each portfolio project is actually progressing, in the 2D site and the 3D book, from evidence kept in the project's own repository. Every claim carries a date and a pass mark, so nothing looks finished before it is. The book's chapters are generated from content, so adding a project needs no hand-written 3D code.

This is sub-project 1 of three:

1. This spec, delivered as two plans: **1a** contract, ingestion and 2D ledger; **1b** generated book and wax seals.
2. A progress skill for Claude and Codex: creating and maintaining `progress.json`, the shared project workflows (`progress-check`, `progress-record`), auto-recording, and registering projects.
3. Live demos of each project, designed separately.

## Non-goals

- The time scrubber. The data supports it (entries are append-only and dated); the UI comes later.
- Fetching data in the browser. Everything is baked in at build time.
- Shared workflows in project repositories, append-only and commit-ancestry checks: sub-project 2.
- Private repositories.
- More than three chapters, or a multi-page contents.

## Decisions

| Topic               | Decision                                                                             | Why                                                                                               |
| ------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| What a visitor sees | Evidence first (dated entries with pass mark and result), commit activity underneath | Shows whether the project works, not only that it is busy                                         |
| Data home           | `progress.json` at each project's repository root                                    | Evidence lives next to the code it describes                                                      |
| Contract owner      | kcb.pro publishes the schema and the rules                                           | The consumer defines what it accepts                                                              |
| Freshness           | Build-time fetch, plus a daily scheduled build and deploy                            | Static pages that work without JavaScript; no browser rate limits                                 |
| Fetch failure       | The build fails; production keeps the last good deploy                               | The site never shows a partial ledger                                                             |
| History             | Entries are append-only; a re-run adds a new entry with the same `subject`           | Honest history, and the data a time scrubber needs                                                |
| kcb.pro's checks    | Schema and domain rules only                                                         | It has no baseline for append-only checks; projects enforce those in their own CI (sub-project 2) |
| Book chapters       | Generated by a pure `layoutBook()`                                                   | Adding a project needs no 3D code                                                                 |
| Chapter choice      | Explicit `rank: 1 \| 2 \| 3` on a project                                            | Importance is decided directly                                                                    |
| Other projects      | A "More work" sheet in the book and the `/work` index                                | Every listed project stays one step away                                                          |

## The `progress.json` contract, version 1

kcb.pro publishes `schema/progress.v1.json` (JSON Schema). Each registered project keeps one file at its repository root:

```json
{
  "schema": 1,
  "project": "bezl",
  "entries": [
    {
      "id": "2026-10-22-pty-throughput",
      "subject": "pty-throughput",
      "date": "2026-10-22",
      "kind": "experiment",
      "title": "Terminal output into the window",
      "passMark": "No lost bytes, echo under 100 ms, memory under 300 MB",
      "result": "partial",
      "measured": [{ "label": "Echo latency, median", "value": "2 ms" }],
      "evidence": [
        { "label": "RESULT.md", "path": "spikes/01-pty-throughput/RESULT.md" }
      ],
      "commit": "01e47db"
    }
  ]
}
```

| Field      | Rule                                                                                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema`   | Integer. kcb.pro accepts the current version and the one before it.                                                                                                                    |
| `project`  | Equals the kcb.pro slug.                                                                                                                                                               |
| `id`       | Unique in the file. Used as the HTML anchor of the entry.                                                                                                                              |
| `subject`  | Groups entries about the same thing over time.                                                                                                                                         |
| `date`     | ISO day, not after the build day. Entries are sorted by date, oldest first.                                                                                                            |
| `kind`     | `experiment`, `tests`, `release` or `milestone`.                                                                                                                                       |
| `passMark` | What counted as success, decided before the result. Required for `experiment` and `tests`.                                                                                             |
| `result`   | `pass`, `partial`, `fail` or `not-run`.                                                                                                                                                |
| `measured` | Measured values only; may be empty.                                                                                                                                                    |
| `evidence` | Items are `{ label, path }` (a repository path, linked at `commit`) or `{ label, url }` (an `https` URL, such as a CI run or release). At least one item unless `result` is `not-run`. |
| `commit`   | A short or full commit hash, linked on GitHub. Required when any evidence uses `path`.                                                                                                 |

Append-only rule (enforced in projects by `progress-check`, sub-project 2): an entry on the default branch is never edited or removed. A correction is a new entry with the same `subject`.

### Derived views

- `current(entries, day)`: the latest entry per `subject` dated on or before `day`. Used now for counts and seals, and later by the time scrubber.
- Counts: over `current(entries, buildDay)`, `pass` is proven, `partial` is partial, `fail` is failed, `not-run` is open.
- Overall seal of a project: `fail` if any current subject failed; otherwise `partial` if any is partial or open; otherwise `pass`. No seal when there are no entries.

## Registering a project

A project is registered when its kcb.pro entry has a `repo`:

```ts
{ slug: 'bezl', repo: 'KhallilB/bezl', rank: 1, ... }
```

For every listed project with a `repo`, the build fails if the repository is not public, has no `progress.json` on its default branch, fails the schema or rules, or uses an unsupported `schema` version. The error names the project and the fix. Sub-project 2 automates registration; this spec defines and enforces what a registered project must satisfy.

## Ingestion

The fetch logic lives in `app/portfolio/progress/fetch.ts`, so vitest covers it. `scripts/progress-fetch.ts` is a thin wrapper.

1. `bun run build` runs `progress-fetch` first. For each listed project with a `repo` it fetches `progress.json` from the default branch and the last 90 days of commits, authenticated with `GITHUB_TOKEN` when present.
2. It validates both, classifies commits by conventional prefix (`feat`, `fix`, `docs`, `test`, `refactor`, `chore`, other), and writes `build-data/progress/<slug>.json` (gitignored).
3. With `PROGRESS_OFFLINE=1`, it copies `app/portfolio/progress/fixtures/<slug>.json` instead. `bun run dev` runs it offline first. Playwright's web server sets `PROGRESS_OFFLINE=1`. CI's Build step runs online.

Loading: the client and SSR entry points read `import.meta.glob('/build-data/progress/*.json', { eager: true })`, validate each file, and pass the result through `SiteProvider`, the way `catalog` and `asOf` already flow. A missing folder gives an empty map, so lint, `tsc -b`, `dev` and tests work on a fresh clone. A project with a `repo` but no loaded data renders no ledger in `dev`; the production build cannot reach that state because the fetch fails first.

Build day: one source, `BUILD_DAY` env or else the UTC day, shared by `vite.config.ts` (`__BUILD_DAY__`) and the fetch. Fixtures are synthetic and dated on or before the test build day (`2026-10-21`).

`ci.yml`:

- Adds `schedule: cron '0 6 * * *'` and `workflow_dispatch`.
- The Build step sets `env: GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}`, so the fetch is authenticated instead of sharing the runner IP's 60 anonymous requests an hour.
- The deploy job's `if:` also allows `github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'` on `main`.
- GitHub disables schedules after 60 days without repository activity; `workflow_dispatch` is the manual fallback.

## 2D: the ledger (plan 1a)

The project page's "Build log" section becomes "Progress":

- Header: proven, partial, failed and open counts, as of the build day.
- Filters: All, Experiments, Tests, Releases, Milestones. Progressive enhancement; without JavaScript every entry is shown.
- Entries, newest first, each with `id` = entry `id`: date rail; a result badge whose shape and word carry the result, not colour alone; title; pass mark beside measured values; a `<details>` with evidence links.
- Activity: daily commit squares for the last 12 weeks backed by an accessible table, then recent commits grouped by type, each linking to GitHub.
- "Quiet since \<date\>" when the newest entry is more than 30 days before the build day.

The home page's "Selected work" shows ranked projects by rank, then the "All work" link to `/work`. `featured()` is redefined as ranked projects ordered by rank.

## 3D: the generated book (plan 1b)

### Layout

`app/tome/layout.ts` exports a pure `layoutBook(input)` returning sheets, page numbers, contents rows with jump targets, places, face colours, ribbons and spread labels. It contains no Three.js or canvas code. `engine.js` keeps painting, geometry and interaction and reads everything else from it.

A spread _k_ shows the back of sheet *k*−2 on the left and the front of sheet *k*−1 on the right. Sheet order:

1. Contents / About.
2. One sheet per ranked project, by rank: chapter page / notes page.
3. More work, only when listed endeavors without a `rank` exist: front holds rows 1 to 6; back holds rows 7 to 12, or, with six or fewer, an "All work" page linking to `/work`. More than 12 shows the first 11 and a final "See all on the list" row.
4. Work studies / study notes.
5. Contact / colophon.

Contents rows: About, one per chapter, More work (when present), Work studies, Contact, Colophon; at most 8, which is the page's limit (rows 118 px apart from y = 360, page number at y = 1292).

Ribbons: Contents, one per chapter, More work (when present), Studies, Contact; at most 7. Colours are fixed by role, so they never shift as chapters are added: contents `SECT[0]`; chapters `SECT[1]`, `SECT[2]`, `SECT[3]` by rank; More work a new seventh leather dye; studies `SECT[4]`; contact faces `SECT[5]` with ribbon `#e6d9b8`.

Places: `contents`, `about`, each ranked slug, `more-work` (when present, mapped to `/work`), `studies`, `contact`. `placeOfPath('/work/<slug>')` for a listed project without a `rank` returns `more-work` when More work exists. `TOME_PLACES` becomes a value built from content, typed `string`. Validation refuses a ranked slug equal to a fixed place, including `more-work`.

Chapter copy moves from `copy.ts` into the project entry as `book: { notes, facts }`, required when ranked: three facts, at most three notes of at most 190 characters, summary at most 70. The book's About text is generated from the ranked titles.

### Wax seals

Each chapter page's "Build log" block becomes a ledger block: the three most recent subjects of `current(entries, buildDay)`, newest first, each with a wax seal (pass green, partial amber, fail red, not-run a hollow ring) and its result word. Seals press in when the page turns into view; static with reduced motion. Clicking a seal navigates to `/work/<slug>#<entry-id>`; `TomeStage`'s navigation keeps the hash and scrolls to that entry instead of the top. More work rows carry the project's overall seal.

## Acceptance

- Bezl and kbui each have a valid `progress.json` (seeded by hand for plan 1a; sub-project 2 takes over upkeep) and render a ledger in 2D and seals in 3D.
- Removing `rank` from kbui moves it from a chapter to More work with no code change.
- An invalid `progress.json` (for example a future date or an unknown `result`) fails the build with a message naming the project.
- The scheduled build runs and deploys.

## Risks

- `engine.js` is 1,600 untyped lines. Extracting `layoutBook()` is guarded by the golden test and manual browser checks.
- GitHub outages fail the daily build. Production keeps the last good deploy; the next run recovers.
- Without sub-project 2, nothing stops a project from editing a published entry. kcb.pro shows whatever the default branch says.
